# Signed registry

`kh install` already verifies a SHA-256 for every package file. That protects against corrupted
downloads and files that changed without the registry being updated, but **not** against someone who
can change both a package file and `registry.json` (they live in the same repository). A signature
closes that gap: `registry.json` is signed with an Ed25519 private key that is **not** in the
repository, and `kh` checks the signature against a public key built into it before it trusts any
checksum.

## How it works

- `packages/registry.json.sig` holds 128 hex characters: the Ed25519 signature of the **exact bytes** of
  `packages/registry.json`.
- `src/kh_pubkey.h` holds the matching public key (`KH_REGISTRY_PUBKEY_HEX`, 64 hex characters).
- With a key configured, `kh install`, `kh search` and `kh info` **refuse** a registry whose signature is
  missing, malformed or wrong. Nothing from that registry is used.
- With no key configured (the state this repository ships in), `kh` runs in **unsigned mode** and prints
  `registry signature NOT checked` so nobody mistakes it for the protected mode.
- The verifier is `src/kh_ed25519.h`, tested against the RFC 8032 vectors and against an independent
  implementation (`python3 tests/kh/test_ed25519.py`).

## One-time setup (you, the maintainer)

```sh
pip install cryptography
python3 tools/sign_registry.py keygen ~/kosh-registry.key     # outside the repository!
```

It prints the public key. Paste it into `src/kh_pubkey.h`:

```c
#define KH_REGISTRY_PUBKEY_HEX "paste-the-64-hex-characters-here"
```

Then sign, rebuild `kh`, and commit the public key and the signature (never the private key):

```sh
python3 tools/sign_registry.py sign ~/kosh-registry.key       # writes packages/registry.json.sig
make
git add src/kh_pubkey.h packages/registry.json.sig
```

**Back up the private key** (password manager, offline drive). If it is lost you cannot sign new
registries; the only recovery is to generate a new key and ship a new `kh` that contains it. If it
leaks, anyone can publish packages `kh` will trust: treat that as an incident, generate a new key and
release a new `kh`.

## Every time the registry changes

`registry.json` is generated by `tools/gen_registry.py`. After running it:

```sh
python3 tools/gen_registry.py
python3 tools/sign_registry.py sign ~/kosh-registry.key
git add packages/registry.json packages/registry.json.sig
```

If you forget, every `kh` that has the key will refuse the registry (the signature no longer matches).
CI runs `python3 tools/sign_registry.py check`, which fails the build in exactly that case.

## Important: users need a `kh` that has the key

A `kh` built before the key was added runs in unsigned mode forever. Ship the first signed release as a
new `kh` binary and tell people to update `kh` itself (re-run the installer). Until then they get the
SHA-256 checks only.

## Mirrors and tests

`KH_REGISTRY_URL` points `kh` at a mirror or a local registry. A mirror is signed with its own key, so
**only together with `KH_REGISTRY_URL`** you may also set `KH_REGISTRY_PUBKEY=<64 hex>` to replace the
built-in key. (`KH_REGISTRY_PUBKEY` alone is ignored.) The registry signature file is fetched from
`<registry url>.sig`.

## What a signature does not do

- **No freshness / rollback protection.** A signature does not say how new the registry is. Someone who
  controls your network could replay an older, genuinely signed registry and hide an update. They cannot
  inject new code (the old registry's checksums match only the old files).
- **It trusts the signer.** A signed malicious package is still malicious. Review changes before signing.
- **Only the registry is signed**, plus (through the checksums it lists) every package file. Files fetched
  from outside the registry are not covered.
- Windows and macOS builds were not part of the Linux test run for this feature (see CHANGELOG).
